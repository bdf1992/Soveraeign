The rules

What counts as an unhealthy automation, and what an unhealthy reading is allowed to do. Every schedule declared under .claude/schedules/ is enabled false and no scheduled run has ever executed on this machine, so the honest reading of this node today is not HEALTHY - it is UNOBSERVED, which this table names rather than letting an empty record set pass as a green one. That is the same defect CLAUDE.md trap T2 records one level up: green means unchanged, not correct. The table states no count of its own: a witness found the first draft asserting seven schedules, which was true of a working tree eleven sessions share and false of the commit that carried the claim. The table grants nothing, changes no standing, and enables no schedule. scripts/sovschedule/health.py reads it and conformance/fixtures/automation-health/cases.json defeats it.

TARGET_MISSING UNHEALTHY

The file the declaration's target names does not exist under .claude/ - .claude/workflows/<name>.js for a workflow, .claude/skills/<name>/SKILL.md for a skill.

Quiet when: The target file exists, whether or not the schedule is enabled.

A declaration pointing at a file that is not there is broken now, and turning it on would be the moment anyone found out. It is also the one rule derived entirely from committed bytes, so it is the one that can refuse on a machine that has no run history. scripts/sovschedule/declaration.py also refuses such a file outright, which is why the health read loads each declaration on its own and carries the loader's defect text on this finding: one dead target must not blind the reader to the other six schedules.

DECLARATION_REFUSED UNHEALTHY

scripts/sovschedule/declaration.py refuses the file - malformed JSON, a shape the schema refuses, an unparseable cron expression, an EXTERNAL_WORLD effect class, or a build-mode run on the shared tree with no clean-tree precondition - and the target does exist.

Quiet when: The loader accepts the file, or the target is missing and TARGET_MISSING already carries the loader's defect text.

A declaration that will not load is not a schedule, and every other verb in scripts/sov_schedule.py stops at the first one it cannot read. This surface reads each file on its own so a reader still sees the six that are fine.

ENABLED_NEVER_RUN DEGRADED

The schedule is enabled and the ledger holds no attempt for it at all.

Quiet when: The schedule is disabled, or at least one attempt is recorded.

A schedule switched on that never fires is the failure this whole surface exists to notice: nothing watches the tick, so a tick that was never registered looks exactly like a tick that works.

LAST_RUN_FAILED DEGRADED

The newest settled run is FAILED or INCOMPLETE.

Quiet when: The newest settled run is PASSED, or no run has settled.

One failure is news. It is not yet a defect, because the executor runs against a live host and a single bad run can be the host. Two in a row is CONSECUTIVE_FAILURES and that one refuses.

CONSECUTIVE_FAILURES UNHEALTHY

The newest consecutive_failure_threshold settled runs are all FAILED or INCOMPLETE.

Quiet when: Fewer than the threshold have settled, or any of the newest that many PASSED.

Twice is the host excuse used up. This is the reading that refuses, and it clears by a run that passes - never by editing this table and never by deleting the ledger, because an enabled schedule with no history reads ENABLED_NEVER_RUN instead.

RUNTIME_REGRESSION DEGRADED

The newest completed run took at least regression_multiple times as long as the completed run before it, and the increase was at least regression_floor_seconds.

Quiet when: Fewer than two runs have completed, or the newest is inside either bound.

Bdo asked for a run that took materially longer than its predecessor. Both bounds are load-bearing: the multiple alone turns a 0.2s jitter into a finding, and the floor alone misses a slow run getting slower.

REFUSAL_LOOP DEGRADED

The newest refusal_loop_threshold attempts were all REFUSED and carried the same reason code.

Quiet when: Fewer than that many attempts exist, any of them was not a refusal, or the codes differ.

The runner refuses on SCHEDULE_DISABLED, EFFECT_CLASS_REFUSED, TREE_DIRTY, or RUN_IN_PROGRESS. A schedule that trips the same gate every time is alive, is doing nothing, and looks alive in every count that measures attempts. Differing codes are not a loop - they are a machine having a bad week - and this rule stays quiet for them.

EMPTY_RUN DEGRADED

The newest run whose status is PASSED recorded no output address under reports/, whether or not that run also recorded an end time.

Quiet when: No run has passed, or the newest passing run wrote a report.

The refusal loop quieter twin. Every declaration prompt in scripts/sovschedule/runner.py asks the executor to write a completion report; a run that returns zero and writes nothing is alive, spends budget, and achieves nothing, and unlike a refusal there is no code in the record naming it. Every count that measures passing runs reports it as working.

OVERDUE DEGRADED

The schedule is enabled, at least one attempt is recorded, and either at least overdue_missed_occurrences whole cron occurrences have passed since the newest attempt, or that attempt is older than the scan window.

Quiet when: The schedule is disabled, no attempt is recorded, fewer occurrences than that have passed with the scan window not exhausted, or the cron expression does not parse - in which case DECLARATION_REFUSED is what reports the file.

Distinct from ENABLED_NEVER_RUN: this is the tick that used to fire and stopped. Counting occurrences rather than elapsed time is what makes one rule cover a two-hourly schedule and a weekly one.

  • Refuses at UNHEALTHY: This is the alert leg the request admits: a nonzero exit from a check scripts/verify.py runs, so an unhealthy automation fails the build. Phase I forbids external-world effects and nothing here opens an outbound channel - no email, no push, no notification that leaves this machine. A Console surface 1 notification record is the second admissible leg and is not built here; the Console notification path has no implementation.
  • Rebuild: python scripts/sov_schedule.py health-render. Grade: python scripts/sov_schedule.py health-check, which scripts/verify.py runs.
  • Switches: python scripts/sov_schedule.py console for this page with working buttons, or enable / disable on the command line. Both reach one operation, declared in contracts/automation-control.json.
  • The reading layer is separable from where the records come from. The seam is scripts/sovschedule/history.py; moving this onto Console surface 3 replaces that module and leaves the rules and their fixtures untouched.
  • A reading is a report about records and holds no standing. A REPORTED event in those records is the executor's own self-report, never an observation that the run did what it said.
