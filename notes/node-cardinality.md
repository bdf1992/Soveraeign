# Owner Note — One Owner, Many Nodes

Status: `OWNER_NOTE_NON_PHASE`

A node ownership profile is **not** a one-owner/one-node cardinality rule. One person may own and administer **N Soveraeign Nodes**. A single-person deployment can therefore be multi-node while each node retains its own local sovereignty, custody, authority, record, and governed crossings.

Purpose does not create a new structural class. A useful deployment may isolate a bounded service or capability in its own node; that remains a **Service inside a Node**, and the instance counts as a Soveraeign Node only if it satisfies the existing Node identity test. Running a service in a separate process, container, VM, or host is not enough by itself to make it a node.

Common purpose-shaped patterns may include:

- **service-scoped nodes** — isolated nodes whose primary purpose is hosting a particular service or bounded capability;
- **virtual nodes** — a useful node pattern where the node is virtualized while retaining the same sovereignty test;
- **generative nodes** — a useful on-demand/generated node pattern, with the exact creation and lifecycle semantics left intentionally undefined here.

These are deployment/purpose patterns, not newly ratified node types. If multiple sovereign nodes interact, their interaction still uses the repository's existing governed node-crossing/federation model.

This note records owner intent only. It does not open a successor phase, create a requirement, or change current service standing.
