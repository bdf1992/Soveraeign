## Goal

Establish, before a long-horizon `sov-federation` session runs all seven domains at once: current
standing per domain, the operations legitimately available under O1-O12, what is blocked, which
files two domains would both write, what ordering those collisions force, and which judgement

## The read

The stack is workable but not safe to run seven-wide in parallel yet. Four domains are READY
(conformance, asset, proofing, verification), three are PARTIAL (governance, contracts, byom), none
are BLOCKED. Verify is green on every scout's run (`python scripts/verify.py` exit 0, 0.65s of the
3.0s budget). The hazard is not any single domain; it is that five of the concurrency conflicts
the loop probed are real, every one of them runs through governance-owned files or unowned
directories, and the tree is already dirty with two sessions' uncommitted writes.

Three things decide whether the long run produces witnessed work or a pile of refusals:

1. Serialize governance last. STATUS.yaml, OPEN-SEAMS.md, and `decisions/` have one writer
   (sov-governance) and sequential identifiers (next seam S11, next decision 0014). Every other
   domain queues seams, decisions, and standing changes as report text; governance consumes the
   aggregated queue at the end of the wave.
2. Settle two ownership seams before contracts, conformance, or byom touch them:
   `contracts/model-binding.schema.json` (claimed by contracts and byom) and the
   participant-observation crossing (schema in `contracts/`, prose contract in `conformance/README.md`).
   Both are judgement-typed; until Bdo rules, the affected operations hold.
3. Decide where run output and drafts live. `reports/`, `.claude/drafts/`, and `contracts/fixtures/`
   exist on disk and no Owns clause covers any of them; lint scans all three.

  contracts, conformance, asset, proofing, byom, verification, then governance.

  counter. Ordering: other domains emit questions as report `judgement_items` only (packets land
  in `.claude/drafts/<slug>.md` by the O2 precedent, never in `decisions/`); governance allocates
  S11+ and 0014+ by reading the working tree at write time, never a number quoted in a skill.
- X3 Model Binding field drift, resolution `split_files`. Largely a category error, not drift:
  the schema matches the SPEC.md ModelBinding block field for field with one addition,
  `authority_source: const SOVERAEIGN_KERNEL`, which appears nowhere else in the repository;
  check_i9 describes a per-invocation observation, a different object. Ordering: contracts CON-1
  records the divergence first and alone; byom's O12 packet consumes it; byom fixture authoring
  waits until `contracts/fixtures/` has an owner.
- X4 participant-observation crossing, resolution `judgement`. Two documents each claim to be
  the contract; `conformance/run.py` reads only `case_id` and `observed` and references neither.
  Interim HOLD: contracts must not edit `contracts/participant-observation.schema.json` and
  conformance must not edit the README Observation section or `observations_by_id()` in the
  same session; asset's observation refresh waits until both are quiescent.
- X5 oracle extension versus asset repair, resolution `serialize`. No shared-file write;
  `services/asset/conformance/BASELINE.md` asserts a freeze over conformance-owned files.
  Ordering: conformance changes to `scenarios.json` or a CHECKS function complete and pass
  verify first; asset's BASELINE refresh runs after and should pin the oracle identity it bound
  to. Edits to `oracle-controls.json` or `test_oracle.py` need no ordering (empirically verified:
  the participant binding never reads them).
